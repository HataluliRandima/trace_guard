# TraceGuard 0.1.0-rc.1: an experimental preview

> **Draft.** Not yet published. Intended as the text of the GitHub
> pre-release for the tag `v0.1.0-rc.1`.

TraceGuard is a small Elixir library for Phoenix applications. When a
request fails, it gives you a **redacted diagnostic report for that one
request**: the route, the Ecto queries it ran (in order, with timings), the
work it did in Tasks and GenServer calls you opted into, the exception, and
what TraceGuard could *not* see. It never changes the response or swallows
the exception.

This is the **first release candidate and an early, experimental preview**.
It isn't production-proven. I'm releasing it to find out where it breaks in
real applications.

## The problem

When a Phoenix request fails, the evidence is spread across logs that
interleave every concurrent request and often contain raw secrets.
Telemetry events exist, but nothing ties them back into one failed
request's story. TraceGuard attaches to the telemetry Phoenix and Ecto
already emit, attributes each event to the request that caused it (by
process, never by timing), keeps only failures, and redacts sensitive
values before the report leaves the request process. It runs inside your
application: no agent, no service, no network calls.

It is not an APM or a distributed tracer, and it doesn't trace function
calls.

## What's in this release

* `TraceGuard.Plug`, plus Phoenix and Ecto telemetry capture, for router
  failures, throws and exits.
* A response header (`x-traceguard-id`) to find a report, and lookups by
  trace ID, request ID or a client correlation ID.
* Recursive, key-based redaction, and scrubbing of labelled secrets in
  exception messages (`api_key=…`, `Bearer …`).
* Opt-in propagation into Tasks (`TraceGuard.wrap/1`) and selected
  GenServer calls (`TraceGuard.call/3`, experimental).
* Bounded storage with explicit outcomes. Every dropped report is recorded
  (`report_status/1`, `report_stats/0`, telemetry). Three storage options:
  * **memory**, the default;
  * **SQLite**, for local development (experimental);
  * **Ecto/PostgreSQL** (experimental): reports go into *your* PostgreSQL
    database, through *your* existing Repo, in a table created by a
    migration you generate (`mix trace_guard.gen.ecto_migration`) and run
    yourself. TraceGuard never runs migrations or changes your schema on its
    own.
* JSON export of any report.

## Install

From the Git tag (it isn't on Hex):

```elixir
# mix.exs
{:trace_guard, github: "HataluliRandima/trace_guard", tag: "v0.1.0-rc.1"}
```

```elixir
# lib/my_app_web/endpoint.ex: after Plug.RequestId, before Plug.Telemetry
plug TraceGuard.Plug

# config/config.exs
config :trace_guard, ecto_telemetry_prefixes: [[:my_app, :repo]]
```

Then make a request fail and look at
`TraceGuard.await_report(id)`, where `id` is the `x-traceguard-id`
response header. The
[getting-started guide](https://github.com/HataluliRandima/trace_guard/blob/v0.1.0-rc.1/docs/getting_started.md)
walks through it. In a clone of the repository
(`git clone --branch v0.1.0-rc.1 https://github.com/HataluliRandima/trace_guard.git`),
the
[demo](https://github.com/HataluliRandima/trace_guard/blob/v0.1.0-rc.1/demo/README.md)
(`cd demo && mix setup && mix phx.server`, then `./scripts/run_demo.sh` in
another terminal) triggers three failures and checks that none of seven planted secrets
appear in their reports.

## Known limitations

Please read these before trying it anywhere that matters:

* **Your application's logs are not sanitized.** Phoenix, Bandit, Cowboy,
  Ecto and OTP log raw exception messages, secrets included, exactly as
  they would without TraceGuard. Only TraceGuard's own reports are redacted.
* **Unlabelled secrets** in exception messages (a card number with no key
  next to it) are not recognized. `capture_exception_message: false` turns
  messages off.
* **Reports can be dropped.** Under a burst beyond `max_pending_reports`, or
  when storage fails (a database outage, a missing table), reports are
  dropped, and each drop is recorded. During a database outage, most drops
  show up as `:overloaded`; `report_stats().last_error` shows the cause.
* **PostgreSQL deletes don't erase data.** Retention and `clear_reports/0`
  are ordinary `DELETE`s; copies can remain in WAL, replicas and backups.
* **One writer** stores reports one at a time: about 180 per second on
  PostgreSQL on the development laptop. That's an observation, not a
  guarantee.
* **Only attributable events.** Unwrapped Tasks, plain `GenServer.call/3`s,
  casts and work on other nodes aren't attributed to a request. Some
  failures (throws, exits, endpoint-plug errors) have no response header.
* **Experimental APIs** may change before 1.0: `TraceGuard.Server`,
  `TraceGuard.Storage` and its SQLite and Ecto adapters, and the migration
  module and task.
* **Tested** in CI on Linux only:
  * Elixir 1.15.8 / OTP 26 to Elixir 1.20.1 / OTP 29;
  * Phoenix 1.7 and 1.8;
  * Bandit and Cowboy;
  * PostgreSQL 16 and 18.

  **Not tested:** macOS, Windows, releases (`mix release`), multiple nodes,
  managed or pooled PostgreSQL (TLS, PgBouncer), sustained production load,
  and no production use at all. See
  [compatibility](https://github.com/HataluliRandima/trace_guard/blob/v0.1.0-rc.1/docs/compatibility.md)
  and
  [security](https://github.com/HataluliRandima/trace_guard/blob/v0.1.0-rc.1/docs/security.md).

## Feedback wanted

Bug reports and rough edges are the point of this release. I'd especially
like to hear about:

* **Integration friction:** anything in installation or configuration that
  surprised you.
* **The database migration experience:** generating and running the
  TraceGuard migration in your app, with your Repo setup.
* **Compatibility:** Elixir, OTP, Phoenix, PostgreSQL or adapter versions
  where it misbehaves.
* **Production-like behaviour:** dropped reports, overhead, or storage
  behaviour under real load.

Please
[open an issue](https://github.com/HataluliRandima/trace_guard/issues).
Don't paste real secrets or customer data from your reports or logs.
