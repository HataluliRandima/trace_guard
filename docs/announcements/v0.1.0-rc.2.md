# TraceGuard 0.1.0-rc.2: timeline order fix

> Published 2026-10-25 as the text of [the pre-release](https://github.com/HataluliRandima/trace_guard/releases/tag/v0.1.0-rc.2).

The second release candidate of TraceGuard, still an **early, experimental
preview**. It fixes one bug found by trying rc.1 in a real Phoenix
application. There are no API or configuration changes.

New to TraceGuard? The
[rc.1 announcement](https://github.com/HataluliRandima/trace_guard/blob/v0.1.0-rc.2/docs/announcements/v0.1.0-rc.1.md)
explains what it does, and its known limitations still apply.

## Fixed: events listed out of order when an error reporter runs first

Error reporters such as ErrorTracker handle the same Phoenix exception
event as TraceGuard, and write to the database from it. When their handler
ran first, the report put their queries **before** the exception, and the
exception's `offset_us` was late by however long the reporter took (about
80 ms in the application where this was found). Read naively, the timeline
said those queries led up to the failure.

The end of a Phoenix span (`phoenix.endpoint.stop`,
`phoenix.router_dispatch.stop` and `phoenix.router_dispatch.exception`) is
now timestamped at the span's start plus its `duration`, which is when it
actually ended. The reporter's queries now follow the exception.

Other events are still timestamped when TraceGuard's handler receives
them. Ecto emits no start event to measure from.

## Upgrade

```elixir
# mix.exs
{:trace_guard, github: "HataluliRandima/trace_guard", tag: "v0.1.0-rc.2"}
```

Then `mix deps.get`. Nothing else changes. Reports stored by rc.1 remain
readable (same `traceguard.report/v1` schema).
